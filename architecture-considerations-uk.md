# Архітектурні міркування

> Зведені результати, висновки, рішення та обґрунтування з робочого треду.
> Обсяг: тривкі мультиагентні стеки на AWS (LangGraph + Step Functions + Lambda),
> захисний шар **Aegis** на Rust, зіставлений із OWASP GenAI/LLM Top 10 (2026),
> його співіснування з **Amazon Bedrock Guardrails**, і всі супровідні деліверабли.
> Аудиторія: інженер, що будує інфраструктуру моніторингу/спостережуваності
> мультиагентних систем для клієнтів у healthcare-SaaS на AWS.

## 0. Стисло — несучі висновки

1. **Step Functions і LangGraph не є взаємозамінними.** Вони живуть на різних шарах і
   *компонуються*. Step Functions = загальнопризначений рушій тривких воркфлоу/машин станів.
   LangGraph = агентний фреймворк у процесі (типізований стан, цикли, чекпоінтинг, стрімінг).
   «Обидва оркеструють кроки» — лише поверхнева схожість.
2. **Один власник тривкості на межу.** На будь-якій межі, де роботу можна повторити чи
   відновити, рівно одна система відповідає на питання «як далеко ми зайшли?». Ніколи не
   накладайте кілька систем чекпоінтингу на одну й ту саму роботу.
3. **Канонічний патерн AWS (Архітектура A):** Step Functions оркеструє **Lambda без стану**;
   LangGraph виконує цикл агента *усередині* Lambda; **DynamoDB (шифрований KMS)** —
   чекпоінтер. Кожен виклик виконується один раз, без повторного програвання.
4. **Позиція безпеки (теза OWASP 2026):** перестаньте намагатися зробити модель, яку не можна
   обдурити; будуйте систему *навколо* неї так, щоб коли модель обдурять — а її обдурять —
   нічого важливого не зламалося. Ін’єкція промпту внутрішньо притаманна й надійно не
   запобігається.
5. **Aegis** — це детермінований **захисний шар на Rust**, що втілює цю позицію. Він не може
   спинити обман моделі; він володіє **боком наслідків** детерміновано, тож обдурена модель
   лишається нешкідливою.
6. **Найважільніший єдиний контроль — брокер повноважень** (Правило двох / смертельна
   трійця). Будуйте його першим.
7. **Aegis і Bedrock Guardrails підсилюють одне одного** (вони не конкуренти): Guardrails =
   ймовірнісний ML-екран (◐ знизити, до моделі); Aegis = детерміноване стримування (●
   стримати, до системи). «Пройдено» від Guardrails *ніколи не є авторизацією*.

## 1. Step Functions vs LangGraph vs Durable Functions

### 1.1 Головна відмінність

Початкове питання: чи Step Functions і LangGraph — «те саме від різних постачальників».
**Ні** — схожість поверхнева (обидва виражають послідовність, розгалуження, паралельний
fan-out, тож діаграми схожі). Реальні відмінності:

| Вимір | AWS Step Functions | LangGraph |
|---|---|---|
| Що це | Загальнопризначена **розподілена машина станів** (мікросервіси, ETL, бізнес-процеси) | Спеціалізований **фреймворк агентних графів зі станом** |
| LLM-концепції | Немає | Стан повідомлень, цикли викликів інструментів, чекпоінтована пам’ять, HITL-переривання, стрімінг токенів |
| Модель виконання | Зовнішні, тривкі, керовані переходи станів у **ASL JSON** | Об’єкти Python/JS у процесі; персистентність опційна через чекпоінтери |
| Потік керування | Обмежені декларативні примітиви; незграбне, обмежене зациклення | Явно **циклічний** граф, природний для ітерацій агента |
| Розмір стану | Стеля **256 КБ** між станами → змушує S3-claim-check для великих даних | Стан довільного розміру в пам’яті |
| Вартість/затримка | Тарифікація **за перехід стану**; ~50–100 мс/перехід | Майже миттєві переходи-виклики; балакучі цикли значно дешевші |
| Тривалість | Підтримує виконання до року | Обмежена хостом (напр. 900 с Lambda) |
| Стрімінг | Немає нативного стрімінгу токенів; потрібні WebSocket/AppSync | Нативний багаторежимний стрімінг |
| Довгі паузи / HITL | `waitForTaskToken` чудовий для тривких пауз на години/дні | `interrupt()` + чекпоінтер; тривкість на розробникові |
| Спостережуваність | CloudWatch / X-Ray | LangSmith |
| Інтеграції | Нативний Bedrock + 200+ сервісів AWS без Lambda-клею | Абстракції моделей LangChain + готові патерни агентів |

**Вони компонуються.** Step Functions як тривкий *зовнішній* оркестратор (приймання
документів, паралельна обробка, людське підтвердження через task token); LangGraph виконує
*внутрішній* цикл агента в Lambda чи ECS-задачі. (Новіший керований напрям AWS тут —
**Bedrock AgentCore**; зазначено, але для патернів нижче не обов’язковий.)

### 1.2 Головний принцип — «один власник тривкості на межу»

На будь-якій межі, де роботу можна повторити чи відновити, рівно одна система відповідає за
«як далеко ми зайшли?». Step Functions володіють прогресом оркестрації; чекпоінтер кожного
агента володіє прогресом його циклу; Lambda між ними не володіє нічим тривким.

**Антипатерн:** Step Functions + durable-Lambda + чекпоінтер LangGraph = **три системи
чекпоінтингу над однією роботою** → пекло ідемпотентності/звірки.

### 1.3 Дві чисті архітектури

- **Архітектура A** — Step Functions оркеструє **Lambda без стану**; LangGraph виконує
  агента; **DynamoDB (шифрований KMS)** — чекпоінтер. Кожен виклик Lambda виконується один
  раз, без повторного програвання. **Це рекомендований варіант за замовчуванням** щоразу, коли
  є реальна оркестрація чи складність агента.
- **Архітектура B** — **Durable Functions володіють тривкістю наскрізно**; LangGraph працює
  в пам’яті. Два підваріанти:
  - **B-proper:** увесь граф в одному атомарному тривкому кроці.
  - **B-handrolled:** цикл агента на тривких кроках, без рушія LangGraph.
  - Беріть B для одноагентної системи з довгими дешевими очікуваннями й малою навколишньою
    оркестрацією.

**Вердикт:** A — надійний варіант за замовчуванням; B — для одного агента / довгих дешевих
очікувань; регулятор atomic-vs-handrolled ставте свідомо.

### 1.4 Жорсткі ліміти й механіка, що визначили рішення

- **Стеля одного виклику Lambda: 900 с (15 хв).** Нічого налаштовуваного це не піднімає.
- **Стеля елемента DynamoDB 400 КБ** → `DynamoDBSaver` (`langgraph-checkpoint-aws`)
  вивантажує чекпоінти понад ~350 КБ у S3. Вмикайте це заздалегідь.
- **Стеля payload між станами SF: 256 КБ** → передавайте **S3-посилання** для великих
  payload; ніколи не проштовхуйте цілі документи через машину станів.
- **Офіційна схема чекпоінта DynamoDB від AWS** = композитний PK/SK. Мінімальний IAM для
  чекпоінтера: `GetItem`, `PutItem`, `Query`, `BatchGetItem`, `BatchWriteItem`.
- **KMS-з-DynamoDB найменші привілеї:** `kms:Decrypt` + `kms:GenerateDataKey` +
  `kms:DescribeKey` з умовою `kms:ViaService = dynamodb.<REGION>.amazonaws.com`.
- **«Fan-out»** уточнено = паралельні незалежні гілки (SF `Parallel`/`Map`, LangGraph `Send`)
  + збирання (fan-in). Валідно лише коли гілки незалежні.

### 1.5 Звірені актуальні API LangGraph/AWS (станом на тред; чутливі до версій)

- `create_supervisor` — `langgraph-supervisor`
- `create_swarm` / `create_handoff_tool` — `langgraph-swarm`
- Механізм передачі: `Command(goto=..., graph=Command.PARENT)`
- HITL: `interrupt()` / `Command(resume=...)` — **потребує чекпоінтера + `thread_id`**.
- **Ключовий гоча:** під час відновлення перерваний вузол **виконується з початку** —
  розміщуйте побічні ефекти *після* `interrupt()` або робіть їх ідемпотентними.
- Доступ до моделі Bedrock: `ChatBedrockConverse` (`langchain-aws`), Converse API, облікові
  дані з ролі виконання Lambda (ніколи не вшиті).

> **Застереження щодо версій:** концепції стабільні; шляхи імпорту, аргументи конструкторів,
> назви пакетів та id моделей/inference-профілів Bedrock дрейфують між релізами — пініть і
> перевіряйте.

## 2. Захисний шар Aegis (Rust) — зіставлений з OWASP GenAI/LLM Top 10 (2026)

**Статус назви:** *Aegis — підтверджена, затверджена назва* (більше не робочий заголовок).

### 2.1 Стратегія і рамка чесності

Aegis — це невеликий **Cargo workspace з композованих крейтів**, що обгортають агентів
LangGraph. Rust обрано, бо захисний шар сам ніколи не має бути слабким місцем: безпечний щодо
пам’яті (жодного RCE на рівні парсера в тому, що має спиняти RCE), достатньо швидкий, щоб
стояти в лінію, один статичний бінарник як **розширення Lambda** чи **сайдкар Fargate**, і —
найважливіше — найцінніші контролі OWASP **детерміновані** (оцінка політик, валідація схем,
кодування, вирізання байтів, білі списки), а це належить компільованому тестованому коду, а не
делегується назад моделі.

Кожен контроль позначено одним із трьох **рівнів чесності**:

| Рівень | Значення | Роль Rust |
|---|---|---|
| **● Стримати** (детерміновано) | *Наслідок* загрози обмежено кодом, що поводиться однаково щоразу й не деградує під адаптивною атакою. | Rust володіє цим повністю — тут більшість цінності. |
| **◐ Знизити** (ймовірнісно) | Знижує успішність атаки, але адаптивний зловмисник, що прочитав захист, усе ще може пройти. Ніколи не остання лінія. | Rust допомагає, завжди в парі з контролем «Стримати» позаду. |
| **○ Процес** (не лікується кодом) | Залишок живе в керуванні даними, навчанні/перенавчанні моделі чи людському процесі. | Rust може виміряти й пригальмувати, не розв’язати. |

**Наслідок рамки:** ін’єкція промпту (LLM01) — це **◐ на вході** і **● на наслідку**. Aegis
майже не витрачає бюджет на *виявлення* ін’єкцій і майже весь — на те, щоб успішна ін’єкція не
дотяглася до нічого вартого. Це і є позиція OWASP, зроблена виконуваною.

### 2.2 Workspace (крейти)

| Крейт | Задача | Основні пункти OWASP | Рівень |
|---|---|---|---|
| `aegis-core` | Рівні довіри, мітки походження, теги повноважень, спільні типи | — | — |
| `aegis-broker` | Посередник повноважень / детермінований рушій політик (Cedar) | LLM03, LLM01, LLM07 | ● |
| `aegis-output` | Валідація схеми виводу + кодування під приймач | LLM10, LLM02 | ● |
| `aegis-egress` | Фаєрвол вихідного трафіку / брокер ексфільтрації | LLM02, LLM06, LLM01 | ● |
| `aegis-meter` | Токен-орієнтований контроль витрат + автоматичні вимикачі | LLM06 | ● |
| `aegis-ingress` | Нормалізація вводу / фаєрвол промптів | LLM01, LLM09 | ◐/● |
| `aegis-retrieval` | Вартовий авторизації пошуку + векторів | LLM09, LLM05, LLM02 | ●/◐ |
| `aegis-supply` | Верифікатор артефактів / ланцюга постачання (підпис, пін, скан) | LLM04, LLM05 | ● |
| `aegis-redact` | Фільтр розкриття / цензурування виводу та трас | LLM02, LLM08 | ◐/● |

### 2.3 Словник довіри (`aegis-core`)

Три невеликі типи роблять межу довіри **фактом часу компіляції**, а не домовленістю:

```rust
// Звідки прийшов вміст, а отже, наскільки йому довіряють.
pub enum Provenance { System, User, SemiTrusted, Untrusted }

// Вміст ніколи не є голим String, щойно потрапляє в Aegis: він несе своє походження.
pub struct Tagged<T> { pub value: T, pub origin: Provenance }

// Біти Правила двох. Кожен виклик інструмента класифікується за цими трьома осями.
pub struct Capability {
    pub reads_untrusted: bool,  // (A) торкнувся недовіреного вводу цієї сесії
    pub reads_sensitive: bool,  // (B) може дотягтися до приватних/регульованих даних
    pub external_effect: bool,  // (C) зміна стану або вихідна комунікація
}
impl Capability {
    // Смертельна трійця: усі три разом — це високоімпактна умова.
    pub fn is_trifecta(&self) -> bool {
        self.reads_untrusted && self.reads_sensitive && self.external_effect
    }
}
```

### 2.4 Розгортання на AWS

- **Лінійний шар** (ingress, output, egress, meter, retrieval, redact, broker): єдиний
  бінарник на Rust як **розширення Lambda** поруч із кожною Lambda-агентом (у процесі, без
  мережевого стрибка), або **сайдкар Fargate** за внутрішнім ALB, коли агент на ECS. Чутливо
  до затримки й частково стан-залежне (rate limits, вимикачі) → співрозміщення краще за
  віддалений сервіс.
- **Стримування вихідного трафіку архітектурне, не лише кодове:** агент у **приватній
  підмережі без маршруту за замовчуванням**; увесь вихід через проксі `aegis-egress`. Обдурена
  модель не може ексфільтрувати до ендпоінта, якого VPC не досягає.
- **Політики (Cedar)** версіоновані в S3; брокер оцінює локально (без мережевого виклику на
  кожне рішення).
- **`aegis-supply`** виконується в CI/CD (GitHub Actions) і знову під час завантаження моделі.
- **`aegis-ledger`** дописує в DynamoDB чи S3 з **Object Lock** для незмінності, корелюючи з
  CloudTrail за `run_id`/`thread_id` (ті самі ключі, що й чекпоінтер LangGraph).
- **Компонується з Архітектурою A, не замінює її:** Step Functions далі володіють оркестрацією
  й тривкою паузою підтвердження; LangGraph далі виконує цикл; DynamoDB + KMS далі тримають
  стан. Aegis сидить *між* моделлю й кожним повноваженням, яке вона хоче застосувати.

### 2.5 Шлях запиту (конвеєр «1.1»)

```
НЕДОВІРЕНИЙ ВХІД
  → aegis-ingress (нормалізація · вирізання Unicode/тегів · обгортка походженням)   ◐/●
  → [ МОДЕЛЬ ]  (видає недовірений ЗАПИТ, а не команду)
  → aegis-output (валідація схеми + кодування під приймач)                          ●
  → aegis-broker (РУШІЙ ПОЛІТИК · Правило двох)                                       ●
  → aegis-egress (білий список; зовнішній ефект гейтиться тут)                        ●
  → ІНСТРУМЕНТИ · МЕРЕЖА · ПРИЙМАЧІ  (лише дозволені)

наскрізь через увесь конвеєр:
  aegis-meter (вартість · вимикачі) · aegis-retrieval (авторизація-в-запиті) ·
  aegis-supply (підпис · пін) · aegis-redact (траси · PII) ·
  aegis-ledger (аудит · пам’ять) · aegis-redteam (адаптивний гейт)
```

Три блоки боку наслідків (output, broker, egress) — несучі; вхідний вартовий цінний, але
свідомо **не** вважається достатнім сам по собі.

## 3. План за загрозами (LLM01–LLM10)

Для кожного пункту: що OWASP вважає досяжним, контролі Aegis, чесний поділ стримати/знизити/
процес, і пріоритет.

### LLM01 — Ін’єкція промпту
- **OWASP:** внутрішньо притаманна; надійного запобігання немає.
- **Aegis:** ◐ на вході (`aegis-ingress` детермінована гігієна Unicode = вирізати tag-block
  U+E0000–E007F, селектори варіацій U+FE00–FE0F та U+E0100–E01EF, нульову ширину U+200B/C/D
  та U+2060, нейтралізувати bidi; обгортання походженням; евристики кодувань/low-resource), ●
  на наслідку (broker + egress + output).
- **Стримано:** канали невидимих символів + уся площина наслідків. **Знижено лише:** керування
  видимим текстом/крос-модальними payload. **Залишок ○:** хибна *відповідь*.
- **Пріоритет:** будуйте трійцю стримування (broker, output, egress) першою. **Не** будуйте
  детектор ін’єкцій як основний контроль.

### LLM02 — Розкриття чутливої інформації
- Поверхні ширші за фінальну відповідь: аргументи інструментів, траси міркувань, здобуті
  фрагменти, логи, ембединги, побічні канали час/довжина.
- **Aegis:** `aegis-redact` трактує траси й аргументи як першокласний вивід (●) + багатошарове
  виявлення PII/PHI/секретів (◐); `aegis-broker` тримає секрети поза промптом (●);
  `aegis-egress` блокує маячки image-URL / ексфільтрацію Unicode / приховані канали (●);
  `aegis-retrieval` авторизує до пошуку (●).
- **Залишок ○:** побічні канали (паддинг/батчинг допомагає ◐) і запам’ятовування/інверсія
  (DP-SGD, дедуплікація, рознавчання, перевірка енкодера — конвеєр, не Rust).

### LLM03 — Надмірна агентність (наріжний камінь)
- Першопричини: надмірні функціональність, дозволи, автономія — усі детерміновано виправні.
- **`aegis-broker` (●):** повне посередництво (немає шляху від виводу моделі до побічного
  ефекту, що його оминає; авторизація вирішується в коді, ніколи не питанням до моделі);
  найменші привілеї на операцію (аргументи валідовано за схемою, перевірено під час виконання);
  гейт Правила двох (будь-яке [A,B,C] → підтвердження людини через task token SF; [A,B] або
  [A,C] → явне рішення про залишковий ризик); градуйований примус (аудит→попередження→
  блокування→ескалація; рецензент бачить *точну* відрендерену дію); ідемпотентність + подвійний
  контроль; **інструменти з відкритим кінцем заборонені**.
- **Реалізація:** **Cedar** (Rust-native мова політик від Amazon) як ядро оцінки; політики
  версіоновані в S3, оцінюються локально.
- **Пріоритет: №1. Будувати першим.**

### LLM04 — Ланцюг постачання
- **`aegis-supply` (●):** підпис + перевірка хешу (Sigstore); пінування до незмінних дайджестів
  (відхиляти `latest`; виявляти повторне використання неймспейсу); гейтинг SBOM/AIBOM
  (CycloneDX ML-BOM); сканування серіалізації + верифікація AI-запропонованих залежностей
  (перемагає slopsquatting).
- **Залишок ○:** поведінкові бекдори, що переживають підпис → ред-тімінг + оцінювання.

### LLM05 — Отруєння даних і моделі
- **Aegis:** `aegis-supply` цілісність артефактів (ваги, адаптери, чат-шаблони, конфіги
  токенізаторів) ●; `aegis-retrieval` стримування RAG-корпусу (мітки походження, сегрегація за
  довірою, виявлення захоплення пошуку) ●/◐; `aegis-ledger` пригальмування записів у пам’ять ●.
- **Залишок ○:** отруєння навчальних даних (~250 отруєних документів можуть бекдорити модель
  незалежно від розміру датасету; вирівнювання не прибирає бекдорів) → керування даними, лінеаж
  (DVC), курація, пост-вирівнювальне зондування тригерів.

### LLM06 — Необмежене споживання
- **`aegis-meter` (●):** токен-орієнтовані ліміти (токени/хв, токени/день, оцін-вартість/запит)
  із передпольотною оцінкою токенів (HF `tokenizers`, Rust-native), що відхиляє до інференсу;
  **жорсткі стелі витрат** (неперевизначувані, спиняють інференс — не просто алярми); агентні
  автоматичні вимикачі (стелі кроків/рекурсії/стінного-часу/вартості; хешування стану для
  виявлення циклів); вартовий зростання контексту (кумулятивна вартість на сесію); дроселювання
  екстракції (◐).

### LLM07 — Дезінформація
- **Aegis:** `aegis-broker` claim-check-act — відокремити генерацію від виконання; повторно
  валідувати аргументи/авторизацію/передумови/стан перед високоімпактними викликами (●);
  `aegis-output` обов’язкові структуровані поля (●).
- **Залишок ○:** фактична точність / заземлення — це якість моделі/RAG; Aegis обмежує радіус
  ураження, не підвищує точність.

### LLM08 — Розкриття прихованого контексту
- Виправлення майже цілком **архітектурне** (● за задумом): жодних секретів у промпті/прихованому
  контексті (`aegis-broker`/`aegis-redact`); авторизація примушується детерміновано брокером,
  ніколи не делегується інструкціям системного промпту; прихований контекст трактується як
  несекретний за політикою, тож розкриття має мало прямого впливу.

### LLM09 — Слабкості векторів та ембедингів
- Рамка: отруєння робить хибним, інверсія — протічним, глушіння — німим, збій контролю доступу
  — невибірковим.
- **`aegis-retrieval`:** авторизація **всередині** запиту до індексу (● — область від клієнта
  це пропозиція, не контроль); нормалізація на прийманні (вирізати нульову ширину/гомогліфи) ●;
  походження + сегрегація індексів за довірою ●; приховати сирі оцінки схожості + виявляти
  захоплення пошуку ◐; **трактувати ембединги як еквівалент джерела** (шифрувати, бекапи за
  чутливістю джерела, класифікувати витік «лише ембедингів» як порушення документа-джерела, бо
  інверсія відновлює текст) ●/○.

### LLM10 — Неналежна обробка виводу
- Хрестоматійний **● Стримати** й один із найсильніших випадків для Rust.
- **`aegis-output`:** строга валідація схеми в довіреному коді (ніколи не другий виклик LLM);
  кодування під приймач з урахуванням контексту (HTML/SQL/shell/шляхи/email); вирізання
  керуючих символів/ANSI/OSC/BEL для термінала/лога/IDE; нейтралізація ексфільтрації під час
  рендерингу (вимкнути авто-завантаження markdown-зображень/прев’ю/iframe; білий список чи
  серверний фетч, що вирізає параметри-носії даних); жодного авто-виконання згенерованого коду.

## 4. Модель повноважень докладно (наріжний камінь)

Брокер сидить між агентом і кожним інструментом. Він ніколи не питає модель, чи дозволена дія;
він вирішує детерміновано, зі стану накопичених повноважень сесії та політики Cedar.

```rust
pub enum Decision { Allow, HumanApprove, Deny(&'static str) }
pub struct Session { pub cap: Capability, pub run_id: String }

pub fn mediate(sess: &mut Session, call: &ToolCall, policy: &cedar::PolicySet) -> Decision {
    // 1. Структурно: аргументи мають відповідати строгій схемі інструмента.
    if !call.schema_valid() { return Decision::Deny("порушення схеми аргументів"); }
    // 2. Оновлюємо зараження Правила двох цієї сесії ЦИМ викликом.
    sess.cap.reads_untrusted |= call.touches(Provenance::Untrusted);
    sess.cap.reads_sensitive |= call.reaches_sensitive_data();
    sess.cap.external_effect |= call.has_external_effect();
    // 3. Детермінована авторизація в коді (Cedar), ніколи не через модель.
    if !cedar_authorized(policy, sess, call) { return Decision::Deny("політика забороняє"); }
    // 4. Правило двох: трійця ніколи не авто-схвалюється.
    if sess.cap.is_trifecta() { return Decision::HumanApprove; }  // -> пауза task-token SF
    // 5. Градуйований примус: незворотне/високонаслідкове -> людина.
    match call.consequence() {
        Consequence::LowReversible      => Decision::Allow,
        Consequence::HighOrIrreversible => Decision::HumanApprove,
    }
}
```

Три властивості роблять це несучим:
- **Детермінований** — той самий виклик дає те саме рішення; не деградує, коли зловмисник його
  читає.
- **Монотонний** — зараження повноваженнями лише *накопичується* в межах сесії, тож агент, що
  торкнувся недовіреного вводу, не може згодом тихо повернути довіру, щоб дотягтися до чутливих
  даних і ексфільтрувати.
- **Поза моделлю** — жоден в’їхавши промпт не вмовить брокер відступити від політики Cedar, бо
  брокер ніколи не радиться з моделлю щодо рішення.

**Конкретний сенс фрази «обдурена модель нічого важливого не ламає»:** ін’єкція може повністю
керувати виводом моделі; той вивід може лише *запросити* виклик інструмента; брокер надає запити
за політикою й повноваженнями, а не за переконуванням — тож найгірше, чого досягає
скомпрометована модель, — це відмовлений запит і запис у леджері.

### Правило двох / смертельна трійця — інтуїція (простими словами)

Уяви агента як стажера з ключами від трьох кімнат: **A** вулиця (недовірений вхід — незнайомці
підсовують записки), **B** сейф (чутливі дані), **C** двері назовні (зовнішній ефект:
надіслати/змінити/видалити). Стажер небезпечний лише з **усіма трьома ключами одночасно**:
записка з вулиці каже «винеси вміст сейфа надвір і кинь у скриньку», і B+C роблять це можливим.
Прибери будь-яку одну ногу — і високоімпактна експлуатація розсипається. **Правило двох:**
дозволяй щонайбільше дві з трьох одночасно; комбінація [A,B,C] завжди потребує підтвердження
людини. Рішення ухвалює *код, який не вмовити* (брокер + Cedar), а не модель.

## 5. Дорожня карта впровадження (за важелем, детерміноване першим)

- **Фаза 0 — хребет боку наслідків (тиж. 1–3):** `aegis-broker`, `aegis-output`,
  `aegis-egress`. *Готово, коли* немає шляху від виводу моделі до побічного ефекту чи вихідного
  байта, що оминає брокер/egress, і кожен приймач отримує лише валідований, закодований вивід.
- **Фаза 1 — бюджет, докази, гігієна (тиж. 3–5):** `aegis-meter`, `aegis-ledger`,
  `aegis-ingress` (детерміновані частини). *Готово, коли* кожен прогін має жорстку стелю
  вартості + незмінний аудит-слід, і жоден payload із невидимих символів не переживає приймання.
- **Фаза 2 — вартові площини даних (тиж. 5–8):** `aegis-retrieval`, `aegis-supply`,
  `aegis-redact`. *Готово, коли* моделі ніколи не вручають неавторизований фрагмент, жоден
  непідписаний/змінно-тегований артефакт не завантажується, а траси/аргументи цензуруються до
  логування.
- **Фаза 3 — валідація як гейт (постійно):** `aegis-redteam` адаптивний гарнес у CI; евали
  точності маршрутизації + сценаріїв дезінформації на кожну зміну; пост-вирівнювальне зондування
  тригерів. *Готово, коли* нічого не постачається лише на статичному бенчмарку.

**Правило послідовності (важливе, часто хибно читають):** ніколи не пускайте контроль
рівня **◐ Знизити** (виявлення на ingress) так, ніби це контроль рівня **● Стримати**. Фаза 0
має приземлитися *до* евристик ingress, щоб ймовірнісний шар завжди мав детерміноване
стримування позаду.
- *Простими словами:* ймовірнісний екран «вгадує»; детермінований контроль «гарантує». Спершу
  постав справжні замки (Фазу 0), потім додавай вгадувача (ingress). Якщо вгадувач помилиться —
  замки все одно втримають. «Має приземлитися» = «має вже стояти на місці»; «позаду» =
  детермінований бекстоп стоїть за ймовірнісною передньою лінією.

## 6. Чого Rust не виправить — чесна межа (○ залишки)

- Модель усе ще можна обдурити (LLM01) — Aegis робить це нешкідливим, не неможливим.
- Запам’ятовування/отруєння навчальних даних (LLM02, LLM05) — DP-SGD, дедуплікація, лінеаж,
  курація, рознавчання, зондування тригерів.
- Фактична точність (LLM07) — заземлення/якість RAG на боці моделі.
- Поведінкові бекдори, що переживають підпис (LLM04, LLM05) — лише поведінкове оцінювання +
  ред-тімінг.
- Інверсія ембедингів / бекдори енкодера (LLM09) — геометрія це властивість моделі.
- **Втома від підтверджень** — гейт Правила двох залежить від людей, які рецензують дії [A,B,C];
  на обсязі якість рецензії падає. Проблема процесу/штату, не коду.

Суть не в тому, що Aegis слабкий — його сила *точно локалізована*: він повністю володіє боком
наслідків і чесний щодо боку вводу й моделі. Цей поділ — і є позиція OWASP, і саме він робить
план надійним.

## 7. Співіснування з Amazon Bedrock Guardrails (взаємне підсилення)

**Вони підсилюють одне одного; вони не конкурують.** Guardrails = майже цілком **◐ Знизити**
(до моделі, ймовірнісні ML-судження). Aegis = майже цілком **● Стримати** (до системи,
детермінований). **Одне правило узгодженості: «пройдено» від Guardrails ніколи не є
авторизацією.**

### 7.1 Правильний порядок (це та кореляція, що робить їх взаємопідсилювальними)

```
НЕДОВІРЕНИЙ ВХІД
  → aegis-ingress (нормалізує + вирізає невидимі символи, детерміновано ●)
        → віддає Guardrails ЧИСТИЙ текст, тож їх класифікатори не обійти
          контрабандою Unicode          (Aegis підсилює Guardrails)
  → BEDROCK GUARDRAILS (вхід): атаки на промпт · вміст · PII   ◐
        → зрізає ОБСЯГ + дає сигнали заземлення/PII   (Guardrails підсилює Aegis)
  → [ МОДЕЛЬ ]
  → BEDROCK GUARDRAILS (вивід): вміст · PII · оцінка заземлення   ◐
  → ДЕТЕРМІНОВАНИЙ БЕКСТОП AEGIS: output · broker · egress · ...   ●
        («пройдено» від Guardrails — це НЕ авторизація)
  → ІНСТРУМЕНТИ · МЕРЕЖА · ПРИЙМАЧІ (лише дозволені)

зворотний зв'язок: aegis-ledger + aegis-redteam → з часом тюнять політики Guardrails
```

`aegis-ingress` виконується **першим**, тож Guardrails класифікують чистий, очищений текст —
зловмисник більше не протягне payload із невидимими символами/гомогліфами повз класифікатор
Guardrails.

### 7.2 Як вони підсилюють одне одного (в обидва боки)

- **Aegis → Guardrails:** нормалізація ingress перед Guardrails підвищує влучність
  класифікаторів Guardrails; а оскільки Aegis стримує наслідки детерміновано, ви можете тюнити
  Guardrails **на сигнал, а не як єдиний гейт** — менше консервативних жорстких блокувань і
  хибних спрацювань, бо пропуск ловиться далі.
- **Guardrails → Aegis:** зрізають обсяг ворожого вмісту, що доходить до детермінованого шару,
  а їхні оцінки заземлення/PII/атак стають входами, на які Aegis реагує детерміновано (напр.
  `aegis-broker` відмовляє у високоімпактному виклику при низькій оцінці заземлення).
- **Петля зворотного зв’язку:** `aegis-ledger` фіксує, які «пройдено» від Guardrails згодом
  стали відмовами брокера, а `aegis-redteam` знаходить адаптивні обходи; обидва живлять
  затягування політик Guardrails. Детермінований шар показує, де протікає ймовірнісний.

### 7.3 Хай Guardrails володіють тим, чого Aegis структурно не може

Класифікація атак на промпт/джейлбрейків, фільтри вмісту/токсичності/слів/зображень, оцінка
контекстного заземлення, виявлення PII у промптах/відповідях, перевірки автоматизованого
міркування — ML-судження, де класифікатори Bedrock переграють будь-яку саморобну евристику на
Rust. Guardrails тримають ці ◐-слоти; `aegis-ingress` звужується до детермінованої байтової
роботи, якої класифікатори не роблять.

### 7.4 Лишіть Aegis для детермінованої площини наслідків, до якої Guardrails не дотягуються

- **Модель повноважень:** Guardrails дають гачки «Get user confirmation» і «Return Control», але
  жодного обліку Правила двох, найменших привілеїв на операцію, повного посередництва,
  ідемпотентності чи авторизації Cedar. **Ці гачки — точка інтеграції:** `aegis-broker` ухвалює
  `HumanApprove`, реалізовано через user-confirmation / Return Control від Bedrock.
- **Обробка виводу:** Guardrails фільтрують шкідливий вміст, але не роблять кодування під приймач
  з урахуванням контексту, вирізання керуючих символів/ANSI, валідацію схеми чи нейтралізацію
  ексфільтрації через markdown-зображення. Чиста, нетоксична відповідь усе одно може нести
  шкідливий SQL-рядок чи URL ексфільтрації → `aegis-output` лишається необхідним.
- **Взагалі без еквівалента в Guardrails:** облік токенів/вартості (`aegis-meter`),
  підпис/пінування артефактів (`aegis-supply`), авторизація всередині векторного запиту
  (`aegis-retrieval`), білий список вихідного трафіку (`aegis-egress`).

### 7.5 З’єднання перетинів + впорядкування за вартістю

- LLM01: класифікатор Guardrails першим (◐), стримування Aegis позаду (●) — не будуйте другий
  класифікатор ін’єкцій.
- LLM07: Guardrails дають оцінку заземлення (◐); `aegis-broker` перетворює «заземлення нижче
  порога» на детерміновану відмову (●).
- LLM02: Guardrails цензурують промпт/відповідь (◐); `aegis-redact` покриває поверхні, яких
  Guardrails не бачать — траси міркувань, аргументи інструментів, ембединги (●).
- **Вартість:** Guardrails додають затримку/витрати на виклик; детерміновані перевірки Aegis
  майже безкоштовні. Запускайте дешеві детерміновані гейти (схема, egress, повноваження)
  першими, щоб зробити коротке замикання до оплати виклику Guardrails; бережіть дорогі перевірки
  Guardrails для недовіреного вмісту й заземлення, не на кожен внутрішній стрибок.

### 7.6 Розподіл відповідальності

| Задача | Bedrock Guardrails (◐ знизити) | Aegis (● стримати) |
|---|---|---|
| Ін’єкція промпту / джейлбрейк (LLM01) | Фільтр атак на промпт, теги вводу | бекстоп broker/egress/output; байт-гігієна ingress |
| Безпека вмісту / токсичність | Фільтри вмісту, слів, зображень | — (поступається Guardrails) |
| Дезінформація (LLM07) | Оцінка контекстного заземлення, авто-міркування | broker гейтить виклик за оцінкою |
| Чутлива інформація (LLM02) | PII-фільтри в промпті/відповіді | цензурування трас, аргументів, ембедингів; жодних секретів у промпті |
| Надмірна агентність (LLM03) | Get-user-confirmation, Return Control (гачки) | Правило двох, найменші привілеї, повне посередництво, Cedar |
| Обробка виводу (LLM10) | — | валідація схеми, кодування приймача, керуючі символи, ексфільтрація |
| Споживання (LLM06) | — | meter: стелі, автоматичні вимикачі |
| Ланцюг постачання (LLM04) | VPC/PrivateLink для імпортів (інфра) | supply: підпис, пін, SBOM, скан |
| Вектори/ембединги (LLM09) | — | retrieval: авторизація-в-запиті, сегрегація |
| Вихідний трафік | — | egress: проксі default-deny з білим списком |

> **Заувага щодо нумерації OWASP:** старий список до 2026 позначав Розкриття чутливої інформації
> як LLM06, а Надмірну агентність як LLM07/LLM08. У списку 2026 це **LLM02** і **LLM03**; самі
> функції Bedrock ті самі — лише номери змістилися. (Ця правка знадобилася, бо завантажений
> підсумок Bedrock використовував стару нумерацію.)

## 8. Довідник інтеграції по крейтах (для новачка)

**Ментальна модель:** агент — це *цикл*, а не магія. Модель читає контекст і або відповідає, або
**просить викликати інструмент** (виклик — це структурований текст на кшталт «виклич `send_email`
з такими аргументами»). Модель нічого не виконує — ваш код вирішує, чи запускати запит.
**Вивід моделі — це недовірений *запит*, а не команда.** Мультиагентність = кілька таких циклів,
що передають роботу → більше місць, де недовірений текст може щось запустити. Aegis =
детерміновані контрольні точки на межах циклу. Слова про розгортання: **розширення Lambda**
працює поруч із функцією в тому самому середовищі (у процесі); **сайдкар Fargate** — допоміжний
контейнер поруч із контейнером застосунку.

Для кожного крейта: що робить · куди під’єднується · чому саме там · пастка новачка, яку прибирає.

- **`aegis-core`** — спільний словник довіри (`Provenance`, `Capability`). Усі крейти залежать
  від нього. Робить «недовіреність» *фактом типу*, а не коментарем. *Прибирає:* передавання
  голих `String` і втрату походження — де ховаються ін’єкції.
- **`aegis-ingress`** — чистить/маркує все, що заходить до моделі (вирізати невидимий Unicode,
  нормалізувати, обгорнути походженням). На вході — єдина точка, де вхід ще чистий від впливу
  моделі. Байтова гігієна детермінована й повна. *Прибирає:* віру, що фільтр на вході «вирішує»
  ін’єкцію — він лише **знижує**; справжній захист далі.
- **`aegis-output`** — валідує вивід за строгою схемою й кодує під приймач (HTML/SQL/shell),
  вирізає керуючі символи, нейтралізує ексфільтрацію. Між моделлю й кожним приймачем. Кодування
  має бути там, де вивід виходить з-під контролю (на приймачі). *Прибирає:* вставляння відповіді
  моделі прямо в SQL/HTML/термінал.
- **`aegis-broker`** — вирішує Allow/HumanApprove/Deny для кожного виклику. Межа, де «текст, що
  просить» стає «дією». Рішення ухвалює *код* (Cedar + Правило двох), а не модель. *Прибирає:*
  довіру моделі щодо того, коли кликати потужний інструмент. Код агента ніколи не кличе інструмент
  напряму — лише через брокер:
  ```rust
  match broker.mediate(&mut session, &call, &policy) {
      Decision::Allow        => run_tool(&call),        // виконати
      Decision::HumanApprove => pause_for_human(&call), // -> пауза Step Functions
      Decision::Deny(reason) => reject(reason),         // відмовити й залогувати
  }
  ```
- **`aegis-egress`** — контролює, куди агент дістає в мережі (білий список + вирізання
  параметрів-носіїв даних). Агент у приватній підмережі без виходу за замовчуванням; увесь вихід
  через проксі. Архітектурне стримування — найнадійніший вид. *Прибирає:* повний вихід Lambda в
  інтернет «щоб просто працювало».
- **`aegis-meter`** — рахує токени/вартість і рве нескінченні цикли (передпольотна оцінка;
  стелі кроків/рекурсії/вартості). Обгортає виклики моделі й весь прогін. Цикл сам собі ліміту не
  поставить → вимикач має бути *поза* циклом. *Прибирає:* два агенти передають керування
  нескінченно, а рахунок росте.
- **`aegis-retrieval`** — (RAG = класти документи у векторну базу, діставати найсхожіші шматки в
  контекст; пошук за схожістю нічого не знає про права.) Авторизує пошук *усередині* запиту до
  індексу, сегрегує за рівнем довіри, нормалізує на прийманні. Перед векторною базою. Фільтруєш
  *після* — модель уже побачила фрагмент, відкликати не можна. *Прибирає:* один спільний індекс на
  всіх орендарів із фільтром «десь у застосунку».
- **`aegis-supply`** — перевіряє походження артефактів (підпис + хеш, пін до незмінного дайджесту,
  скан). У CI/CD і при завантаженні, не в гарячому шляху. Отруєний артефакт треба спинити *до*
  продакшену. *Прибирає:* тягнути модель за іменем чи тегом `latest` (перереєстровним на
  зловмисницьку версію).
- **`aegis-redact`** — цензурує чутливе у фінальній відповіді *та* в трасах міркувань і аргументах
  інструментів. Спільний шлях класифікації-й-цензурування перед логуванням/поверненням. Витікає не
  лише фінальна відповідь. *Прибирає:* логування сирих трас у спільну спостережуваність «для
  дебагу».
- **`aegis-ledger`** — незмінний журнал викликів/рішень/підтверджень + гейт записів у довготривалу
  пам’ять. Дописує в незмінне сховище за `run_id`/`thread_id` (`thread_id` = ідентичність одного
  прогону/розмови). Без сліду дебажиш наосліп; запис у пам’ять — привілей (отруєний спогад впливає
  на всі майбутні сесії). *Прибирає:* вільний запис агента в пам’ять → «сплячий агент».
- **`aegis-redteam`** — ганяє весь захист **адаптивними** атаками (складеними після прочитання
  захисту). У CI як реліз-гейт; тестувальникам дають повну специфікацію. Статичний бенчмарк бреше.
  *Прибирає:* побачити «успіх близько нуля» на статиці й вирішити, що захист готовий — адаптивний
  успіх може перевищувати 90%.

**Один запит наскрізь:** (1) ingress чистить+маркує → (2) meter бюджетує → (3) retrieval дістає
лише дозволені фрагменти → (4) модель *просить* виклик → (5) output валідує+кодує → (6) broker
вирішує Allow/HumanApprove/Deny → (7) egress пускає лише до цілей з білого списку → (8) ledger
записує незмінно (redact перед тим зцензурував чутливе). `aegis-supply` зробив своє раніше
(збірка/завантаження); `aegis-redteam` постійно перевіряє, що весь ланцюг тримається під
адаптивною атакою.

## 10. Заявлені вподобання та обмеження (для наступності)

- Постачати збірку бота/проєкту як **єдиний zip, названий за проєктом** (напр. `aegis`).
- Чат простим текстом із **емодзі-маркерами** для структури; без markdown/жирного/заголовків у
  чат-відповідях (PDF/документні деліверабли використовують повне форматування — прийнято).
- **Обґрунтовані бенчмарками** рекомендації з **чесним аналізом компромісів**.
- Працює **українською та англійською**.
- **Світле тло** в друкованих деліверablах (тонер).
- **Правило адаптивного тестування:** відхиляти лише-статичні заяви про успіх атак; ред-тімити з
  розкритим захистом (адаптивний успіх перевищував 90% проти більшості захистів при статичному
  близько нуля — Nasr et al., цитовано OWASP).
